# ADR-0001 官方发行拓扑与核心工具链许可

> 状态：**草案**（未批准）  
> 日期：2026-09-12  
> 需求：方案 §2.1、§2.2、§7 N1；WP-N1  
> 拓扑底稿：`RELEASE-TOPOLOGY-LICENSE-BASELINE.md`  
> 本草案不代替 P00-01 闭包扫描、hello build、Windows spike。

## 1. 上下文

P00 必须先冻结：官方包里有哪些进程、新 CLI 用什么语言与进程模型、核心模块如何摆放。  
方案 §2.1 已给出冻结建议。本 ADR 按该建议写成草案；推翻需要工程反证，不是口味。  
Apache-2.0 按 A–E 分级，不因许可证名自动淘汰。

## 2. 推荐决定（草案）

1. **主语言：TypeScript + tsc。** `tsc` 是 C 级构建工具，不进运行时制品。  
2. **进程：单进程 CLI。** Desktop 只经版本化 Trylo Protocol；UI 不当事实源。  
3. **knowledge：核心旁路模块，不是 Desktop 状态源。** 逻辑路径 `internal/knowledge/`（片段库 pending/active）。`internal/loop` 禁止 import。不进 UI。学习将来只经 `ports/context` 读取，不改 Loop 拓扑、不授予权限。  
4. **不选：** OpenCode 当 core；LangGraph 当领域；bun 当发行运行时（开发可用）。  
5. **官方包进程**以拓扑文件为准：当前 Desktop 主进程 + desktop-services + trylo-workd + TryloDesktopPet + 可选 hermes adapter；新 CLI 是规划中的单一 `trylo` 进程。`internal/knowledge` 不是第 N 个 OS 进程。

## 3. 工具链许可与 C 级位置

本轮未下载 npm 包内 LICENSE 文件。下列 SPDX 来自上游公开声明，正式闭包仍待 P00-01/04。未知不得当已通过。

| 工具 | 公开 SPDX（待闭包核验） | A–E | 最终制品？ | 口径 |
|------|-------------------------|-----|------------|------|
| TypeScript / `tsc` | Apache-2.0 | C | 否（编译器本体不进运行时） | 方案正式选择。C 级 Apache 可审计采用。核心 DTO 自有，禁止把编译器类型当 Protocol |
| Node.js 发行运行时 | 混合（项目自有 + 上游） | C 运行时 | 是（用户机或捆绑运行时） | 与现有 Desktop/MCP 一致；版本锁定属后续包 |
| bun | MIT（公开声明） | C 开发可选 | 否 | 方案：开发可用，**不**当发行运行时 |
| pnpm（Desktop 现用） | MIT（公开声明） | C | 否 | 新 CLI 包管理器未在本包选定（禁止建 package.json） |
| npm | Artistic-2.0（公开声明） | C | 否 | 若选用须记义务；不自动当 MIT |
| yarn | BSD-2-Clause（公开声明） | C | 否 | 备选 |

重评这些 SPDX 的条件：目标版本包内 LICENSE/NOTICE 与公开声明不一致，或传递闭包把限制性许可证打进制品。

## 4. 被拒候选与工程降级理由

许可证名称不是拒绝理由。下列为工程理由。重评必须满足对应条件并改方案，不能只改本 ADR 口味。

### 4.1 Go 核心 + 协议化 Desktop adapter

**不选。** Go 单二进制与标准库强，但新 CLI 必须对接现有 TypeScript Desktop、MCP SDK、Windows PTY/TUI。跨进程边界、双栈调试、Ink/终端生态与人才栈成本，收益盖不住（方案 §2.1）。Desktop 已有 Rust 壳，再加 Go 核心变成三语言。

**重评条件：** 可证 Windows PTY/TUI 与 MCP/SDK 的进程边界与调试成本可接受；团队接受长期双栈；且有可维护的 Protocol 适配而不把 Go 类型泄漏进 Desktop。

### 4.2 现代 JavaScript ESM + JSDoc/schema（无 tsc）

**不选。** 迁移快、工具链轻，但大型 runtime 的静态保证、重构安全与合同测试弱于 TypeScript + `tsc`。核心主权依赖显式类型边界。

**重评条件：** 可证同等规模下重构安全与合同测试不低于 `tsc`；且不依赖「作者记得」维持端口隔离。

### 4.3 Rust 核心

**不选（观察项降级为不选）。** 性能与可控性强，但工具链、FFI、Windows PTY/TUI、MCP/TS SDK 桥与团队迭代成本无足够收益。Desktop 宿主已用 Rust/Tauri；把 Agent Loop 再放进 Rust 会分裂核心与生态，且 knowledge/ports 更难与 TS Desktop 共享类型而不泄漏。

**重评条件：** 可量化的性能/安全收益覆盖 FFI 与双栈成本；Loop 与 Protocol 仍由 Trylo 自有合同定义，Rust 只做可替换实现。

### 4.4 其它明确不选

| 候选 | 工程理由 | 重评条件 |
|------|----------|----------|
| OpenCode 当 core | 会带入外部 session/provider/plugin 生命周期，夺取 A 层类型主权 | 仅当降为 B 级 adapter，Trylo 自有 DTO，合同测试可替换 |
| LangGraph 当领域 | 图框架反向定义 Loop | 永不作为领域模型；研究笔记除外 |
| bun 当发行运行时 | Windows 发行与 Node/MCP 生态一致性未证；方案已排除 | 干净 Windows 发行路径 + 与 Node 行为合同一致 |

## 5. knowledge 模块（方案 §2.2）

```text
internal/knowledge/    片段库（pending/active）
```

- **是：** 与 `loop` 并列的核心旁路模块，随单进程 CLI 发行。  
- **不是：** 独立 OS 进程；不是 Desktop/UI 状态源；不是 `desktop-services` 学习环的事实源。  
- **硬边：** `internal/loop` 禁止 import 本目录。核心不得 import Desktop 事件、React、provider SDK、数据库。  
- **本包不做：** 不建目录、不复制 memdir、不实施 assemble。N2 建目录与越界测试；N4 做纵切。

## 6. 与发行拓扑的衔接

外人应能指出官方包进程（详见拓扑文件）：

- **现在：** `trylo-desktop`、`desktop-services`、`trylo-workd`、`TryloDesktopPet.exe`、可选 `hermes-capabilities`；可能再 spawn 旧 CLI 与 D 级 MCP。  
- **规划：** 一个 `trylo` 进程（含 loop / ports / **knowledge 旁路** / adapters）；Desktop 只消费 Protocol。  
- **禁止进包：** `new trylo cli/open/`。

RED 项见 `LICENSE-REMEDIATION-BACKLOG.md`。本 ADR **不**把任何 RED 标成已清。

## 7. 后果

- N2 必须用 TypeScript + `tsc` 建骨架；越界测试：`loop` import `knowledge` 或 `adapters` 必须失败。  
- 不得把本文件状态改为「已批准」除非产品所有者签字。  
- P00 规格 §3 仍列出的 Go/JS/Rust「正式候选」被本草案按方案降级；规格与方案冲突时以方案为准，不改方案正文。
