# P00：工程地基与协议冻结准备技术规格

> 状态：待审，可据此开始 P00，不授权 P01 生产实现  
> 阶段：P00  
> 预计：3–5 人周；推荐 3 人配置目标为 5–8 个有效工作日  
> 最后更新：2026-09-08  
> 前置：总领架构、质量纪律、许可证政策

## 1. 目标

P00 建立不会因为后续 provider、学习算法、Team 或 UI 选择而推倒的地基：

1. 枚举完整官方发行拓扑，并选择、证明可维护且许可合规的语言/进程/工具链；
2. 建立新 CLI 的独立 workspace 与单向模块边界；
3. 让可读性、维护性、测试、架构和许可证检查真正能阻断提交；
4. 建立当前 Trylo 行为的 parity catalog、规范化 trace 格式和首批黄金样例；
5. 建立 CLI → Desktop 的版本化协议适配壳，不复制当前 UI 事件为核心领域类型；
6. 为 P01 普通协议准备 fixture/schema compatibility，并为 L01 学习产品决策准备证据和 ADR 机制，但不预埋学习合同；
7. 建立从新 CLI、现有 Desktop、sidecar、安装器、CI/codegen 到最终二进制的许可基线与整改工作流。

P00 结束时允许没有真实模型对话，但不允许只有空目录和口号。门禁必须能用故意失败样例证明自己真的会拦截。

## 2. 非目标

- 不实现 provider 请求；
- 不实现 Agent Loop；
- 不实现学习分析、候选或 v0.3 store；
- 不迁移完整工具集、session、Team、MCP 或 TUI；
- 不复制旧 CLI 源码来抢进度；
- 不在协议未冻结前设计 Desktop 卡片细节；
- 不因许可证名直接选择或淘汰技术栈；Apache-2.0 候选必须先完成架构等级与 NOTICE/SBOM 审计。

## 3. 首个阻断决策：发行拓扑、工具链与核心主权

Apache-2.0 不再全面拒绝。P00 必须按架构位置判断依赖：A 级核心主权层默认优先 MIT/ISC/BSD，Apache-2.0 的 B 级 adapter、C 级开发工具和获准 D 级扩展可以采用。P00 仍要覆盖现有 Desktop、sidecar、安装器、CI/codegen 和最终制品，因为 NOTICE、未知/限制性许可证、下载物与类型渗透不能等到 P08 才发现。

P00-00/01 必须产出 `ADR-0001-官方发行拓扑与核心工具链许可.md`。下面只描述候选的顶层许可和工程特征，不代表 bundled distribution/toolchain closure 已通过：

| 候选 | 当前判断 | 原因与必须验证项 |
| --- | --- | --- |
| TypeScript + `tsc` | **正式候选** | 与现有 Desktop/CLI 能力和人才栈最接近；`tsc` 的 Apache-2.0 可按 C 级工具采用。需证明大型 runtime 的类型边界、打包、启动、Windows PTY/TUI 和最终制品清单 |
| Go 核心 + 协议化 Desktop adapter | 正式候选 | 单二进制、标准库覆盖强；需证明与现有 TS 生态/MCP/SDK 的进程边界、Windows PTY/TUI、跨进程调试和团队维护成本 |
| 现代 JavaScript ESM + JSDoc/schema | 正式候选 | 迁移快、工具链轻；需证明静态保证、重构安全和大型 runtime 可维护性不会弱于 TypeScript |
| Rust 核心 | 观察候选 | 性能和可控性强，但工具链/FFI/团队学习与迭代成本需有足够收益才能采用；许可证不是唯一判断 |

任何候选都不能随手继承生态默认轮子。SDK、认证、MCP、SQLite、测试和代码生成包逐项记录 A–E 等级、最终制品位置、NOTICE、类型边界与替换方案。标准库优先是降低复杂度的手段，不是许可证教条。

### ADR-0001 验收

- 画出官方发行拓扑：CLI、Desktop、Node/Rust/Go sidecar、MCP/外部工具、安装器、自动更新、CI/codegen 和最终 artifacts；
- 根据候选比较决定单进程/多进程、主语言与 Node/MCP adapter 的隔离方式，以及哪些进程进入官方发行物；
- 记录每个编译器、标准库、包管理器、formatter、linter/tester、linker、发行运行时的版本、许可证、架构等级与最终制品位置；
- 在干净环境完成 hello/protocol fixture build、test、package；
- 输出所有直接/传递组件清单和许可证；
- 证明 Windows 开发/发行路径；
- 对静态安全、启动速度、单文件发布、provider HTTP、进程/PTY、插件边界做最小 spike；
- 给出被拒候选的工程依据和重新评估条件，不能只写许可证名称；
- 给未知、强 copyleft、NOTICE/SBOM 缺口和核心类型渗透制定整改路径。`隔离出官方开源拓扑` 或 `拒绝发布` 会改变产品范围，只能由用户/产品所有者明确批准。

## 4. 逻辑架构边界

具体物理目录由 ADR-0001 固定，但以下逻辑模块和依赖方向在 P00 冻结：

| 模块 | 责任 | 明确不负责 |
| --- | --- | --- |
| `protocol` | canonical ID、版本 envelope、内容块、事件与 error schema | provider、UI 渲染、存储 |
| `domain` | message/attempt/action/terminal 等领域值与纯状态转换 | IO、SDK、Desktop |
| `loop` | P02 的执行状态机与窄端口 | provider 细节、学习分析、UI |
| `providers` | 各 provider 传输到 canonical stream 的适配 | 调度、权限、UI 事件 |
| `provider-config` | P01 起定义已解析配置、CredentialSource、model registry 与 capability port；凭据只在内存边界传递 | P07 的 login/config UI、把密钥写入事件或 store |
| `tools` | tool SPI、执行适配和标准结果 | 模型策略、学习晋升 |
| `session` | queue、context、compaction、resume 和 `processGeneration` | Desktop 本地状态 |
| `team` | P06 的团队调度和成员运行 | nested scheduler、扩大权限 |
| `ui-event-adapter` | canonical event → 当前 Trylo Desktop 事件 | 成为事实来源或改 LOOP 状态 |
| `cmd/trylo` | CLI 参数、进程生命周期和输出传输 | 领域策略堆积 |

强制依赖方向：应用核心依赖合同/端口，provider/tool/store/UI 适配器实现端口。禁止任何核心模块 import Desktop event type、React、provider SDK 或具体数据库。

## 5. Trylo Protocol 外壳

P00 不冻结完整字段，但冻结协议的形状和测试方法：

```text
Envelope {
  protocolVersion
  eventId
  sequence
  timestamp
  sessionId?
  turnId?
  attemptId?
  correlationId?
  kind
  payload
}
```

约束：

- CLI/tool/subagent/Service Host 等生产者先提供 `{producerId, producerSequence}`；唯一 journal sequencer 在绑定 attempt 后分配 canonical `attemptSequence`；
- canonical sequence 在 attempt 内单调，跨进程不依赖墙钟排序；resume cursor、producer 去重键和有界乱序缓冲在 P01 冻结；
- event ID 用于去重，correlation ID 用于因果链接；
- terminal 不可变；迟到观察用新 observation event；
- payload 有界、可版本化、可脱敏；
- unknown event 对旧 consumer 必须有确定兼容策略；
- UI adapter 只做显式映射，不能解析字符串猜测 tool state；
- schema 需支持未来增加可选扩展，但 P00 不加入 `LearningDirective`、`TaskLearningPlan`、journal、checker 等旧稿正式类型。

P00 只定义运行正确性、恢复和 UI 重放需要的 canonical 事件。L01 再决定学习是否消费其隐私过滤投影、是否需要独立 sink，以及采集关闭的精确语义；P00 不替该讨论做决定。无论选择什么，学习不得借运行日志绕过用户明确的不采集/删除要求。

## 6. Parity Catalog 与黄金 trace

### 能力状态

每个能力只允许以下成熟度：

```text
identified → contracted → mock_verified → real_verified → desktop_parity → release_qualified
```

不得用 `done: true` 或单一完成百分比替代。

### P00 首批场景

至少采集并规范化：

1. 普通流式回答；
2. 单工具和多工具串行；
3. 工具失败与模型修复；
4. 用户拒绝审批；
5. 用户取消；
6. transport 中断/重试；
7. 上下文压缩前后；
8. 子 Agent/Team 事件；
9. queue 与恢复；
10. 附件/产物；
11. usage 与完成原因；
12. 当前产品中与学习、纠正、偏好和验证相关的可观察行为（只记事实，不假定未来接口）。

P00 必须实际交付由**合成任务**产生的普通流、串/并行工具、失败修复、拒权、取消、重试、压缩、子 Agent 至少八类真实 trace。其余受账号/硬件阻塞的边缘项才可留采集计划，且必须附采集脚本、owner 和最迟阶段。v0.3 尚不存在的目标行为只能放 L01 用户故事或实验夹具，不得冒充 observed golden trace 或冻结合同。

规范化只可移除时间戳、随机 ID、机器绝对路径等非语义噪声；不得抹掉顺序、角色、参数、权限、错误、终态、usage、归因锚点和 artifact 差异。Golden trace 禁止包含旧 CLI system prompt、隐藏推理、密钥、真实用户内容、私有绝对路径和大段第三方输出；每组 trace 必须附 provenance 与 redaction report。

黄金 trace 是测试输入和行为证据，不是允许复制旧 runtime 实现的理由。

## 7. 两级质量与许可门禁

P00 必须提供清楚分离的两个入口：

- `quality:new-cli`：扫描新 CLI 自身、它的开发/构建/测试工具和实际 bundle；从 P00 起是阻断门，必须全绿。
- `audit:release-topology`：扫描 Desktop、sidecar、安装器、CI/codegen 和完整官方发行拓扑。P00 可报告 RED，但每项必须进入整改台账并有 owner、处置、依赖和最迟 gate；P08 前清零，P09 对最终实物重扫。

二者可由一个总 `verify` 命令编排，但报告、退出码语义和 gate 阶段不能混淆。`quality:new-cli` 至少执行：

1. format check；
2. lint/static checks；
3. unit + contract tests；
4. dependency direction / cycle checks；
5. schema/fixture compatibility；
6. exact dependency and source inventory；
7. full license closure + A–E 架构位置规则，正确解析 SPDX `AND/OR/WITH`、NOTICE、platform optional、peer、postinstall 下载物、vendored binary 和 native artifact；
8. secret、超大文件、意外二进制检查；
9. generated artifact cleanliness；
10. documentation/evidence presence。

`audit:release-topology` 使用同样的闭包规则，但在 P00 的目标是完整发现与可执行整改计划，不是伪造全绿。

门禁测试自身至少有两个反例 fixture：

- 一个 Apache-2.0 C 级构建工具和一个 B 级隔离 adapter 必须通过；一个 Apache-2.0 框架越过 A 级核心边界且无例外 ADR 必须失败。另有缺失 NOTICE、GPL/AGPL、`AND/OR/WITH`、platform optional、postinstall、vendored binary 和 unknown fixture；
- 一个模拟核心 import UI/provider adapter，必须失败并显示越界路径。

不得依赖一个未完成自身许可证和制品审计的 scanner。必要时用所选标准库读取 module graph/lockfile，生成项目自己的最小审计器。

## 11. P00 退出标准

全部满足才能进入 P01：

- [ ] ADR-0001 已批准，完整官方发行拓扑、工具链和全部依赖范围已有可复核结论；
- [ ] 干净 checkout 能用记录明确的命令完成 build/test/`quality:new-cli`，且阻断门全绿；
- [ ] `audit:release-topology` 已覆盖 Desktop/sidecar/安装器/CI/codegen/final artifacts；允许 RED，但所有整改项均有 owner、处置、依赖和 P08 前最迟 gate；
- [ ] 核心逻辑边界有机器检查，故意越界 fixture 会失败；
- [ ] 许可证检查能输出完整依赖路径、架构等级与最终制品位置；Apache 非核心正例通过，Apache 核心越界/NOTICE 缺失、GPL/AGPL 和未知许可 fixture 失败；
- [ ] Protocol producer/consumer fixture 框架可运行；
- [ ] parity catalog 不少于 12 个首批场景；至少八类核心场景已有合成、脱敏、可重放的 observed golden trace 和 provenance/redaction report；
- [ ] Desktop adapter 没有反向成为状态所有者；
- [ ] `quality:new-cli` 通过、`audit:release-topology` 报告完整、`$trylo-code-quality` 审查报告完整且有独立 reviewer；skill 运行本身不算机器门禁；
- [ ] P00 产出文档完整，未关闭 P0/P1 为零；
- [ ] P01 技术规格已达到可审状态。

## 12. P00 不会替 L01 决定学习架构

P00 可以立即开工，因为它只建立 canonical 运行事实、权限所有权、适配边界、schema 演进和 parity 证据。这些能力不依赖最终选择上下文增强、薄控制面还是在线学习 LOOP。

P00 不得预留旧稿的具体 `experience-contracts`、journal、generation/CAS 或 checker 位置；这些要等 L01。它只需避免把 protocol 写死成 UI 事件，不能遗漏 failed/cancelled/unknown 和因果 ID。这样既不给学习关门，也不提前选择实现。
