# 代码可读性、可维护性与审计纪律

> 状态：待审（2026-09-21 按产品所有者指示增补六条执法条款，见"修订记录"）  
> 优先级：P0，所有阶段和所有合并请求的第一门禁  
> 最后更新：2026-09-21

## 原则

本工程把“下一名工程师能安全地继续修改”视为功能的一部分。代码功能正确但控制流难懂、状态所有权不明、错误被隐藏、测试只能靠作者解释，等同于未完成。

审查顺序固定为：

1. 可读性与可维护性；
2. 架构边界；
3. 行为正确性；
4. 安全、权限与隐私；
5. 并发、取消、恢复与幂等；
6. 性能和资源上限；
7. 许可证与供应链；
8. 测试、文档和迁移证据。

第一项失败时立即阻断，不用“测试全绿”抵消。

## 可读性的可验证定义

新维护者应能在一次正常 review 中回答：

- 这个模块只负责什么、不负责什么？
- 核心状态由谁创建、谁能修改、何时终结？
- 一条 user message 如何变成 provider request、tool action、verification 和 final？
- 取消、超时、拒权、部分发送、崩溃恢复分别走哪条显式路径？
- 哪个事件证明动作真实发生，哪个字段证明采用了哪个学习资产版本？
- 如果要增加 provider、tool、checker 或 learning asset，唯一扩展点在哪里？
- 如何在不启动完整 Desktop 的情况下测试它？

若答案需要跨多个隐式回调猜测、依赖日志拼接或阅读某个“大总管文件”的全部实现，设计未通过。

## 架构纪律

### 单向依赖

推荐逻辑层次如下，具体语言目录由 P00 ADR 决定：

```text
protocol / domain contracts
        ↑
application ports + reducers
        ↑
agent loop / session / experience orchestration
        ↑
provider / tool / store / process adapters
        ↑
CLI / TUI / Desktop event adapters
```

箭头表示上层实现依赖下层抽象。领域合同不得导入 UI、数据库、provider SDK 或进程对象。适配器可以依赖核心端口，核心不能反向知道某个 UI 卡片或某家 provider 的流事件。

### 单一所有者

- 消息、attempt、tool call、approval、artifact、learning plan、terminal 各有唯一 canonical 类型。
- 每个可变状态只有一个 writer；其他组件订阅事件或读取快照。
- 同一规则不能同时存在于 prompt 拼装、tool handler 和 UI 判断三份实现中。
- Desktop 只能渲染事实和发命令，不能成为隐藏的 Agent Loop。

### 显式状态机

禁止用多个布尔值表达互斥状态。例如不用 `done + failed + cancelled + pending`，而使用一个明确 terminal/state。每个 transition 必须列出前置状态、输出事件、幂等 key、失败结果和恢复行为。

## 实现纪律

### 命名

- 名字表达领域含义和方向：`plannedHash` 与 `dispatchedHash` 不可合并成含糊的 `hash`。
- `manager`、`helper`、`util`、`common`、`data` 不能作为逃避职责划分的默认名字。
- 布尔变量使用可直接判断真假的命题；出现两个以上会组合成状态的布尔值时改用显式类型。
- 错误码和 reason code 是稳定合同，不把人类文案当控制流。

### 函数与模块

- 一个函数保持一个抽象层级；业务策略和 IO 机械细节分开。
- 优先纯 reducer、不可变输入和依赖注入的端口。
- 单文件约 400 行、单函数约 60 行、圈复杂度 10、参数 5 个以上触发强制 review 警报；这不是机械定罪，但超限必须在 review 中解释为何拆分会更差。
- 禁止循环依赖、跨层深 import、隐式 singleton、可变全局配置和模块加载即产生副作用。
- 环境源（时钟、随机、进程面）只允许出现在注入缝的默认值（`options.now ?? Date.now`）或门禁白名单文件里；生产代码中的裸 `Date.now()`、`Math.random()`、`process.*` 由门禁扫描拒绝（2026-09-20 oauth-flow 事故：违反写在端口注释里的成文契约，直到外部审计才被抓到）。
- `as unknown as` 双重断言只允许出现在门禁白名单内的持久化/序列化边界，且每处白名单必须写明理由；读边界优先用运行时守卫 + fail-closed 替代断言（recovery.ts、projection.ts 是在案先例）。
- 不为“以后也许用到”提前造泛化框架；出现第二个真实用例后再抽象。

### 注释与文档

- 注释解释为什么、不可变式、协议怪癖、风险和反直觉选择；不翻译语法。
- 公共合同有用途、边界、失败语义和兼容规则。
- 复杂算法先给最小例子与反例，再给实现。
- 任何临时兼容路径写删除条件、owner 和最晚阶段，禁止永久 `TODO`。

### 错误、取消与恢复

- 禁止空 `catch`、宽泛吞错、无界自动重试和把 timeout 当“未提交”。
- 每个 `catch` 必须有终局分支：rethrow、返回类型化失败、或注明清理契约的注释。`instanceof` 收窄的 catch 是审查重点——只处理已知异常类型而让其余静默蒸发，是结构合法的吞错（2026-09-20 mcp-http 事故的准确形状：`notify` 有兜底、`respond` 漏了，两处都通过了当时的空捕获扫描）。
- 同一判定、分类或失败词汇出现第二次时，提取进共享模块是义务不是可选重构：兄弟函数各自手写一份失败语义，漂移只是时间问题。
- 外部边界错误一次转换成 canonical error；内部不传播 provider/OS 文案作为逻辑分支。
- 每次副作用明确 idempotency key、提交点和 unknown outcome。
- cancellation 是状态转移，不是随处抛异常后祈祷清理完成。
- 恢复只能依据已持久事实；不得从缺失事件推断成功。持久化边界的 payload 必须过运行时形状守卫（`isTranscriptItem` 一类），守卫不住的 `as unknown as` 是把损坏伪装成数据。

### 日志与可观测性

- 结构化事件优先于字符串日志。
- 日志含 correlation ID、attempt、sequence、component、reason code，不含 token、密钥、隐藏推理、用户私密正文或无界 payload。
- `completed` 表示生命周期终态；质量验证使用独立 checker 状态。

## 测试纪律

测试按风险选择，不追求空洞数量：

| 层 | 必测内容 |
| --- | --- |
| 纯单元 | reducer、冲突规则、canonical hash、状态转换、预算与边界 |
| 合同 | CLI/Desktop、provider/loop、tool/loop、store/worker 的共享 fixture |
| 集成 | 流式工具、取消、审批、超时、重试、并发、崩溃和恢复 |
| 黑盒 parity | 当前 Trylo 用户路径的输入、规范化事件和可见结果 |
| 真机 | Windows 进程、文件系统、shell、网络、打包后运行、真实 provider |
| 故障注入 | 提交前/后崩溃、丢 ack、重复事件、乱序、存储满、权限变化 |

测试必须证明合同结果，不能只断言函数被调用。Golden trace 需要语义规范化，移除时间戳和随机 ID，但不能抹掉顺序、终态、因果和错误差异。

新增回归测试必须附失败证据：对未修复代码跑过且红（红例注入）。测试证明合同，测试自己也要先证明自己会失败——这是文化写成的法条：红例注入曾只在个别 WP 里执行，2026-09-21 起对所有新增回归测试强制。

覆盖率是告警信号而非质量替身：新核心模块建议 branch ≥90%，普通适配器建议 branch ≥80%；关键状态机的合法和非法 transition 必须 100% 列举。低于建议值需风险说明，高于建议值也不能跳过场景审查。

## 自动门禁

P00 必须使以下检查成为可重复命令和 CI 必过项：

- formatter check；
- lint 与未使用代码检查；
- 静态/合同校验（具体工具受许可证政策约束）；
- dependency direction、循环依赖和禁止 import 检查；
- ambient-source 扫描（时钟/随机/进程面，注入缝默认与文件白名单之外即红）；
- `as unknown as` 白名单扫描与生产可达代码的 fake/fixture import 扫描；
- unit/contract/integration tests；
- API/event schema compatibility；
- dependency exact-version、source、license closure 与 SBOM；
- secret、超大文件和意外二进制检查；
- 变更文档和 phase evidence 完整性检查。

执法三原则（2026-09-21 增补）：

1. **门禁红 = 安灯拉绳。** 任一门禁红，修复优先于该目录的一切新工作；红门禁期间不得提交。一个红着的 format 门禁曾静默存在两天（autocrlf 使 git status 不可见）——检测到不等于有人在看。
2. **结构防线优先。** 能让违规结构性不可能的（tsconfig、`.gitattributes`、常驻边界扫描、pre-commit hook）就不要只靠事后检测脚本单点防守。
3. **门禁必须自证。** 每条新门禁上线前做红例注入：植入违规必红，清除后必绿。没有咬过人的门禁和没有一样。

不得用 `--force`、skip、临时关闭规则或修改 baseline 来让失败消失。紧急例外必须有 ADR、到期日、owner、隔离范围和恢复门禁的任务。

## P0/P1 阻断项

以下任一项存在，阶段不得退出：

- 核心 LOOP、权限、session 或 learning store 存在双写/双状态源；
- public contract 无兼容策略或合同测试；
- 关键状态由布尔组合和隐式回调表达，无法列出 transition；
- 失败、取消、timeout、unknown outcome 被合并为普通错误或成功；
- 学习、Skill、MCP、Plugin 或 Team 能扩张权限；
- 未审计依赖或不允许许可证进入 manifest/lockfile/bundle；
- 关键测试依赖真实时间、随机顺序或外部状态而不可重复；
- 代码只能靠作者解释，或超大模块同时拥有多条生命周期；
- release 声明没有链接到可复核证据。

**deferred 库存无治外法权（2026-09-21 增补）**：`approved_deferred` 代码适用与生产代码完全相同的纪律。生产可达文件 import fake/fixture 模块（fake-executor、memory-fake、fakes 一类）即红，由门禁看守而非自觉——工具链的两颗假绿雷（`admit.ts` 硬编码 `passingSandbox`、`pipeline.ts` 同义反复 `independent_verdict`）离生产只差一次普通接线 commit，此规则即是那道闸。

## 债务规则

允许债务只限不会破坏公共合同、数据正确性、安全和未来迁移的局部优化。每项债务必须有 owner、原因、影响、清偿阶段和可检测退出条件。用“先跑起来”制造第二状态源、错误协议或未授权依赖不属于可接受债务。

## 周期审计（2026-09-21 增补）

每完成 N 个工作包（建议 N=5）或每接通一根线，执行一次**不由施工者本人完成**的抽检（四眼原则）：门禁实跑、独立复验门禁声明、反模式扫描与测试质量抽检。本工程两次被这样的审计救过——2026-09-18 抓出假绿门禁、2026-09-20 抓出传输吞错与 CRLF 红门禁——但两次都取决于恰好派了审计。实践有效而成文缺位的东西，会在赶进度时静默蒸发。
