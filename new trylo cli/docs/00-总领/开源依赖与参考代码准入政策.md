# 开源依赖与参考代码准入政策

> 状态：待审（已按 2026-09-08 用户反馈撤销“Apache-2.0 全面禁用”口径）  
> 许可口径：核心主权层优先 MIT/ISC/BSD 等最宽松许可；Apache-2.0 可在非核心、可隔离、可替换位置评估采用  
> 最后更新：2026-09-08

## 当前结论

Trylo 不以“自研”为理由重复制造成熟轮子。许可证判断和架构判断必须分开：Apache-2.0 是允许商业使用、修改和再分发的宽松许可证，并提供明确的贡献者专利许可；它不是 copyleft，也不会因为链接或依赖就要求 Trylo 整体改用 Apache-2.0。

它比 MIT 多出的实际管理成本主要是：随分发物附许可证、保留适用的版权/专利/归属声明、修改源文件时标明变更，以及上游存在 `NOTICE` 时传递适用内容；同时需要理解专利诉讼触发的专利许可终止条款。以上是合规工作，不是自动拒绝理由。

Trylo 真正要守住的是核心主权：第三方框架不能拥有 Agent Loop 状态机、canonical protocol、权限语义、恢复语义或学习如何生效的定义权。一个 Apache-2.0 组件若只是在 Trylo 自有端口后完成传输、解析、遥测、构建或测试，且能被合同测试替换，就可以采用；若它的类型、生命周期和插件模型渗透核心，即使它是 MIT 也可能拒绝。

许可证结论是工程准入意见，不替代正式法律审查。发布前仍需由项目所有者确认最终 LICENSE/NOTICE/第三方声明。

## 按架构位置分级，而不是按许可证一刀切

| 等级 | 范围 | Apache-2.0 口径 | 审批要求 |
| --- | --- | --- | --- |
| A：核心主权层 | Agent Loop、Trylo Protocol、权限/审批、session/recovery 状态所有权、学习应用与治理语义、provider-neutral contract | 默认不作为核心框架或核心类型来源；只有不存在合理替代且退出成本可控时，才提交例外 ADR | 产品所有者批准；必须证明 Trylo 自有合同、替换路径和无类型泄漏 |
| B：隔离适配层 | provider SDK、HTTP/SSE、认证、MCP client、PTY、文件监听、搜索、遥测 exporter、格式解析 | 可以采用 | 依赖审计 + 端口隔离 + 合同测试 + 精确版本 + 替换计划 |
| C：开发/构建/测试 | compiler、linter、formatter、test runner、codegen、CI action | 可以采用 | 记录是否进入最终制品；锁定版本；生成物和下载物单独审计 |
| D：官方可选扩展 | 默认不启用但由 Trylo 官方分发/推荐安装的 MCP、Plugin、Skill、sidecar | 可以采用，但不能借“可选”逃避发行义务 | 单独 SBOM/NOTICE、权限说明、安装边界与卸载路径 |
| E：用户自行外接 | Trylo 只提供通用协议，用户自行选择和安装 | 不进入 Trylo 制品审计，但必须准确描述边界 | 不自动下载、不冒充官方内置；协议层仍做安全隔离 |

“不影响核心”必须能够被验证，不能只靠命名。至少同时满足：

- Trylo 自有接口和 DTO 位于依赖之外；
- 第三方类型不进入 LOOP、session store、学习资产、Desktop protocol；
- 升级或替换不改变核心状态机；
- 可用 fixture/contract test 替换实现；
- 依赖故障有显式降级/错误，不接管权限或恢复；
- 最终制品能准确生成 LICENSE、NOTICE 与 SBOM。

## 许可证基础分类

### 默认允许候选

- MIT、ISC、BSD-2-Clause、BSD-3-Clause、0BSD；
- Unlicense、CC0-1.0 或有明确证据的公有领域内容；
- Apache-2.0：按上面的 A–E 架构等级准入，不再全面拒绝。

### 默认拒绝或必须单独法律决策

- LGPL、GPL、AGPL；
- SSPL、BUSL/BSL、PolyForm、Commons Clause 和其他 source-available/custom 条款；
- UNLICENSED、SEE LICENSE、缺失、冲突或无法判定；
- MPL、EPL、CDDL、BlueOak 等未在当前默认策略内的许可证，先进入专项审查，不能由 Agent 自行视为等同 MIT。

### SPDX 与文件级差异

- `A OR B`：台账记录本工程实际选择的分支；
- `A AND B`：同时履行所有分支义务，任一分支被拒则整体不能直接采用；
- `WITH`、单文件 header、vendored code、fixture、字体、图标、数据集分别审计；
- 仓库顶层许可证不能覆盖包内例外，传递闭包按最终进入的制品和使用位置分类。

## 五类采用结论

| 类别 | 条件 | 允许行为 |
| --- | --- | --- |
| 直接采用 | 宽松许可、成熟窄叶子、边界稳定、退出路径清楚 | 精确版本后放在 adapter 或工具链中 |
| 隔离采用 | 包括 Apache-2.0 在内的宽松组件，能力成熟但有架构渗透风险 | 先定义 Trylo port/DTO 与合同测试，再接实现 |
| 核心例外 | Apache-2.0 或其他经专项批准组件确有不可替代价值，但会靠近 A 层 | 产品所有者批准 ADR 后使用；不得把整套外部 runtime 当 Trylo 核心 |
| 仅供研究 | 强 copyleft、限制性/未知许可，或架构过重而无合适隔离方案 | 只保存来源、许可证事实和独立设计笔记 |
| 拒绝 | 来源不明、恶意/不可维护、合规义务无法履行、无退出方案 | 不复制、不执行、不进入默认工具链或发行物 |

## 当前候选的修订结论

以下是架构候选，不代表已经批准进 manifest；目标版本和完整闭包仍需 P00 审计。

| 候选 | 修订后的结论 |
| --- | --- |
| OpenCode 完整 runtime/core | 仍不直接成为 Trylo core，主要原因是它会带入自己的 session/provider/plugin 类型和生命周期，而不只是许可证。可以认真研究，也可以抽取可隔离模块做 spike |
| OpenCode provider 思路 / Vercel AI SDK | Apache-2.0 不再构成自动否决。可作为 B 级 provider 实现候选；前提是 `TryloModelRequest/Event` 自有、AI SDK 类型不越过 adapter、可以逐 provider 替换 |
| `@opencode-ai/sdk` | 可用于兼容/迁移/测试适配；不得成为 LOOP 或 Desktop 的事实来源 |
| TypeScript + `tsc` | 恢复为正式工具链候选。`tsc` 可作为 C 级构建工具评估；技术栈选择根据维护性、现有代码复用、单二进制/部署、Windows 能力综合决定，不再因 Apache-2.0 自动淘汰 |
| OpenAI 官方 SDK | 可作为 B 级 provider adapter 候选；与 direct HTTP 用实现复杂度、流式正确性、闭包和可替换性比较 |
| Anthropic/Bedrock/Vertex/Azure SDK | 可作为 B 级候选，不因闭包含 Apache 自动拒绝；仍要审体积、初始化、副作用、凭据边界、平台包和替换成本 |
| MCP SDK 当前版本 | MIT 或 Apache-2.0 版本都可进入隔离评估；固定目标版本并封装在 `McpClientPort` 后，不为追逐许可证长期锁死旧版 |
| OpenTelemetry、Fuse.js、Playwright/Chrome DevTools MCP、OfficeCLI | 可根据用途进入 B、C 或 D 级评估；不能因“外围”省略 NOTICE、SBOM、权限和发行边界 |
| `execa` 等进程叶子 | 可作为 B 级候选；传递 Apache 包不再自动否决，重点审 Windows 信号、取消、未知结果和进程树行为 |
| GPL/AGPL 或未知闭包组件 | 仍不进入官方制品，除非产品所有者另行改变许可政策并完成法律审查 |

旧 `trylo cli` 的 lockfile 仍不能整包继承：原因从“含大量 Apache”修正为“闭包过大、存在未知/强 copyleft 风险、难以证明实际用途和边界”。可以按能力逐项复用已经成熟且通过新政策审计的依赖。

## OpenCode 的正确使用方式

OpenCode 值得认真学习和选择性复用：

- `providerId/modelId` 寻址与 lazy loader；
- auth、环境变量、项目配置、用户配置的优先级；
- tools、vision、reasoning、cache、structured output 和 token limit 能力矩阵；
- native provider 与 OpenAI-compatible 路径；
- provider/model quirks、发现、别名、弃用、错误归一；
- SSE chunk、timeout、retry 与兼容测试。

当前不接受的不是“它来自大厂/开源项目”，而是让 Trylo 的核心合同直接等于某个外部 SDK：

```text
TryloModelRequest
  → ProviderPort（Trylo 自有）
  → OpenCode/AI SDK/官方 SDK/direct HTTP adapter（可替换）
  → TryloModelEvent
```

只要 B 级隔离成立，Apache-2.0 的 AI SDK 或官方 SDK 可以成为实现选项。若 spike 证明为了使用它必须让核心消息、工具或流事件全面改成外部类型，则升级为 A 级核心例外讨论，而不是偷偷渗透。

## Apache-2.0 合规清单

每个实际分发的 Apache-2.0 组件至少检查：

1. 目标包、目标版本和实际文件确实采用 Apache-2.0，包内没有更严格例外；
2. 发行物包含许可证副本；
3. 保留适用的 copyright、patent、trademark 与 attribution notices；
4. 若上游有 `NOTICE`，把适用内容放入 Trylo 的第三方声明或随附 NOTICE；
5. 若直接修改其源文件，显著标明 Trylo 做过修改；
6. 不暗示上游商标或组织为 Trylo 背书；
7. SBOM、依赖台账、源码/二进制制品保持一致；
8. 记录专利条款已由发布负责人理解并接受。

官方事实来源：

- [Apache License 2.0 正文](https://www.apache.org/licenses/LICENSE-2.0)
- [Apache Licensing and Distribution FAQ](https://www.apache.org/foundation/license-faq.html)

## 每次依赖变更的审计流程

1. 写清能力需求和候选的 A–E 架构等级；
2. 先定义或确认 Trylo 自有边界，说明第三方类型能到哪里；
3. 记录官方仓库、registry、目标版本、tag/commit、integrity 和维护者；
4. 获取目标文件与仓库许可证，检查额外条款、NOTICE 和包内例外；
5. 枚举 runtime/dev/optional/platform/native/postinstall 与 vendored/downloaded artifacts；
6. 生成依赖路径和最终制品映射，不把“传递依赖”直接等同于“进入发行包”；
7. 做安全、Windows、维护性、故障隔离和替换成本验证；
8. 分类为直接采用、隔离采用、核心例外、仅供研究或拒绝；
9. 固定版本与 hash，更新台账、SBOM、LICENSE/NOTICE；
10. 运行架构边界测试和 bundle/installer 实物复扫；
11. 在当前工期产出目录保存报告并复核。

## 台账字段

```text
name / version / ecosystem / source URL / commit-or-integrity
use case / architecture tier / direct-or-transitive / dependency path
repository license / package license / file exceptions / NOTICE
selected SPDX branch / final artifact inclusion / modification notice
platforms / native-or-download behavior / permissions
Trylo port / leaked types check / contract tests / replacement plan
owner / review date / next review / update policy / decision
```

## P00 与发布门禁

P00 的许可证门禁不再以“发现 Apache-2.0 即失败”为目标，而要证明分类正确：

- Apache-2.0 构建工具或隔离 adapter，在义务完整时可以通过；
- Apache-2.0 框架若越过 A 层边界且没有核心例外 ADR，必须失败；
- GPL/AGPL、unknown、未履行 NOTICE、未记录下载物或第三方类型泄漏必须失败；
- 依赖升级导致架构等级或义务变化时重新审核。

开源发布前仍必须具备：仓库根许可证、`THIRD_PARTY_NOTICES.md`、machine-readable SBOM、完整发行拓扑、准确的版本/hash/用途/NOTICE 台账、最终制品实物扫描，以及无未知和未批准限制性许可证的证据。

政策要达到的结果不是“依赖越少越纯”，而是：核心由 Trylo 掌握，成熟轮子在清楚边界内为我们工作，任何一项都能合法发布、独立测试并在必要时替换。
