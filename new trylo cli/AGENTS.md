# Trylo CLI 工程指令

本目录是新的 Trylo CLI 独立实现。任何 Agent 在这里进行实现、重构、依赖引入或代码审查前，都必须先阅读：

1. `docs/README.md`
2. `docs/00-总领/代码可读性可维护性与审计纪律.md`
3. `docs/00-总领/开源依赖与参考代码准入政策.md`
4. `docs/00-总领/TRYLO-CLI-双循环学习控制面架构.md`
5. 与当前工期对应的施工总技术文档

## 强制技能

- 所有代码任务和代码审查必须显式使用仓库内的 `$trylo-code-quality` 技能：`.agents/skills/trylo-code-quality/SKILL.md`。
- 如果提出“更好的”替代技能，必须先在 ADR 中逐项证明它覆盖 `$trylo-code-quality` 的全部强制门禁；在 ADR 获批前仍使用本技能。
- 引入、复制、fork 或深度绑定第三方仓库前，必须执行仓库与传递依赖审计。许可证结论不明时默认拒绝进入产品。

## 第一优先级

代码可读性与可维护性是发布阻断项，不是最后清理项。功能正确但难以解释、难以测试、边界混乱或只有作者能维护的代码，不得合并。

## 不可绕过的工程纪律

- 核心领域不得依赖 Desktop/UI 事件格式；UI 只能通过版本化 Trylo Protocol 适配。
- 学习控制面已获准开始施工，但只能遵循“双循环 + Learning Control Board + 两个执行接点”的边界。不得把反思、检索、评测、工具获取或资产写入塞进 Execution Loop；不得把旧稿的 `LearningDirective`、`TaskLearningPlan`、`MethodGuard`、四端口或八接点自动恢复为正式合同。
- Learning Loop 只能提交提案和证据；Permission Service 仍是唯一权限所有者。下载、安装、切换、修改工具及对外提交贡献必须走显式授权。
- 一个概念只有一个权威类型、一个生命周期所有者和一个写入入口。
- 禁止用布尔参数堆叠状态；状态机使用显式判别联合或等价建模。
- 禁止吞错、伪造成功、把 `completed` 当作质量验证通过，或用日志代替错误合同。
- 新公共 API、事件、错误码与持久化格式必须有合同测试和迁移/兼容说明。
- 每个生产依赖、开发依赖、可选依赖和传递依赖都受许可证准入门禁约束。
- Apache-2.0 按 A–E 架构等级准入：非核心、可隔离、可替换的 adapter、开发工具和可选扩展可以审计采用；核心主权层默认优先 MIT/ISC/BSD，Apache 核心例外必须由产品所有者批准 ADR。任何许可证都不能替代完整闭包、NOTICE/SBOM 和类型泄漏审计。
- 未经当前阶段技术文档授权，不跨阶段提前堆功能。
- 不修改或覆盖用户在本目录外的现有实现；迁移以适配器和可复核的小提交进行。
- 门禁红 = 安灯拉绳：任一 verify 步骤红时，修复优先于本目录一切新工作，红门禁期间不得提交。
- 每个 `catch` 必须有终局分支（rethrow、类型化失败或注明清理契约的注释）；`instanceof` 收窄的 catch 是审查重点。同一判定/失败词汇出现第二次必须提取共享模块，兄弟函数不得各写一份。
- 环境源（时钟/随机/进程面）只允许出现在注入缝默认值或门禁白名单文件；`as unknown as` 只允许出现在白名单持久化边界——两者均由 verify step 3 扫描拒绝。
- 生产可达代码不得 import fake/fixture 模块；deferred 库存代码与生产代码适用同一纪律，无豁免。
- 新增回归测试必须附失败证据（对未修复代码跑过且红）；每条新门禁上线前必须红例注入自证。

## 完成定义

Agent 不得仅以“代码已写”宣告完成。至少需要同时提供：

- 对应需求/合同与设计依据；
- 可读性和可维护性自审结果；
- 测试、静态检查、架构约束和许可证检查证据；
- 新增风险、已知限制和回滚方法；
- 当前工期产出目录中的施工记录。

## Code Review Rules

审查顺序固定为：可读性与可维护性 → 架构边界 → 行为正确性 → 安全与权限 → 并发/恢复 → 性能 → 许可证与供应链 → 文档与测试。第一项未通过时，不得以其余检查通过抵消。
