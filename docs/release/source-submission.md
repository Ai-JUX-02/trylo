# 源码提交、打包与公开范围

> 状态：待审
> 阶段：公开源码整理，第一批
> 负责人：Trylo 项目维护者
> 最后更新：2026-10-15
> 依赖决策：当前产品源码、新版 CLI、整理后的架构文档公开；现已授权先提交当前源码开发快照；正式布局迁移和二进制发行另行验收。

## 提交什么

新版 CLI、Desktop、Desktop Services、Work、移动端、网站、自产原生组件、可分发的第三方来源/补丁、锁文件、构建脚本、合成测试和当前架构文档。网站在本次源码范围中，源码更新与线上部署分别执行。

只发布选中文件组成的产品树。开发副本与其 .git 仍含完整内部历史，不能把这个副本设上公库远程后直接 push。现有公库保留自身历史，在它的候选分支上审阅和提交更新，不强推覆盖。

## 不进入源码提交

- 旧 trylo cli、官方 runtime 发行件。
- CLI open/研究克隆、_backup、参考资料的整库副本。
- 原始模型 wire/session/stdout、真实录音录像与任务数据库、未经脱敏的运行证据。
- 个人配置、密钥、签名 keystore、真实连接状态。
- node_modules、Cargo target、编译缓存、Tauri resources 整棵本机生成物。
- 安装程序、APK/AAB、打包压缩文件；这些走独立 Release 制品。
- WORKCOPY_INFO/MANIFEST、原始发布纪律、内部 PPT 工程与临时截图。

这是源码范围规则，不是“发现 Claude 字样就删除”的规则。合法 API 支持、许可证和来源归属保留；旧内核 spawn、旧协议依赖与不可再分发的发行件必须清除。

## 计划怎样提交

先做完整候选源树并通过验收，再在公库候选分支形成可独立复核的提交：

1. 架构说明、公开范围、开发指南与源码导出入口。
2. 新 CLI、原生 helper、构建闭包及 Desktop/Services 路径和协议切换；同一提交中保证调用闭合。
3. Work、移动端、网站及其依赖/路径/合成测试整理。
4. 许可证声明、版本与制品清单、干净克隆和安装验收结论、面向使用者的 README。

最终可根据实际依赖合并或细分，不能为了凑数量提交红门禁状态。历史施工记录不直接充当产品 README；个人项目历史和团队贡献说明暂不添加。

## 制品分开

| 制品 | 内容 | 放置 |
| --- | --- | --- |
| 公库源代码 | 可构建源码、锁文件、脚本、合成测试与架构 | 公库候选分支，经 review 后合入 |
| 源码归档 | 来自同一已验收源树，不带内部 .git 与本机数据 | Release source archive + SHA-256 |
| CLI 安装包 | 从当前源码构建的 npm tgz/平台包及运行依赖声明 | Release；安装后独立验证 |
| Desktop 安装包 | Tauri 安装产物，含固定 Node/CLI/services/native 资源 | Release；无系统 Node 的安装环境验收 |
| Android 包 | 当前移动端构建的签名 APK | Release；签名密钥留在本机/CI secret |
| 网站 | 站点源码与下载入口 | 源码随仓库提交；部署另行执行 |

二进制 helper 的源码、来源、版本和复现/获取方式进入源码仓库；helper 的预编译发行件进入可追溯的制品闭包，不把被 .gitignore 吞掉的本机文件当作可复现步骤。

## 放行依据

- 目录与 import/脚本路径一致，缺失构建输入有明确、固定的获取或构建方式。
- 新版 CLI 的完整门禁通过；Desktop/Services、Work、移动合同按改动范围通过。
- Desktop 的实际启动入口和资源内容均绑定新版 CLI；旧 runtime 不可达且不入制品。
- 新目录的干净克隆能从锁文件和固定工具链构建，不依赖开发盘绝对路径。
- 公库源树与源码包文件列表/哈希一致；安装包来自同一冻结源码。
- 许可证/NOTICE/SBOM 与实际依赖对应；扫描结论可复核，不打印或保留凭据原文。
- 原生桌面、安装制品、远程和真机验收分别记录；静态检查不替代这些证据。

第一批 source-preview 仅用于核对组织方式。清单生成成功不表示上述放行依据通过，所有未完成项仍显示为阻断。
